# Generated pipeline variables

A pipeline needs values per environment as well: the name of the store, the resource group, the
web app. Typing them into the YAML gives you a second list of environment values, next to
`app-configuration/variables/`, that drifts apart from the first. Instead,
`app-configuration/New-PipelineVariables.ps1` generates one
[variable template](https://learn.microsoft.com/azure/devops/pipelines/process/templates#variable-reuse)
per pipeline and environment from the same variable files. Each holds only the variables that
pipeline uses.

```text
app-configuration/variables/     pipelines/orders-api.yml           pipelines/variables/orders-api/
  common.json                     + the templates it includes          dev.yml
  dev.json             ──────►    + the apps it deploys (#{Token}#) ──► test.yml
  test.json                       + orders-api.variables.json          prod.yml
  prod.json
```

## Why

- **One source.** A value per environment is written once, in `app-configuration/variables/`. The
  pipeline and the configuration of the app read the same value.
- **A pipeline sees only what it uses.** It cannot start to depend on a value meant for another
  pipeline by accident, and a change to a variable only touches the pipelines that use it.
- **Reviewable diffs.** The generated files are committed. A pull request that changes a variable
  shows, per pipeline and environment, which resolved value changes. A change to `common.json`
  that should only affect one app, but changes ten generated files, is visible before it merges.
- **No logic in YAML.** Values are resolved before the pipeline runs: no `${{ if }}` per
  environment, no variable that refers to another at run time.

## How it works

1. **Pipelines.** Every `*.yml` directly in `pipelines/` is a pipeline. Templates in subfolders
   are not.
2. **Scan.** The generator reads the pipeline and every local template it includes, recursively,
   and collects the variable names it refers to. It also collects the `#{Token}#` names in the
   files of the apps the pipeline deploys. Full-line comments are skipped.
3. **Environments.** Every file in `app-configuration/variables/` except `common.json` is an
   environment.
4. **Values.** Per environment it merges four layers, later wins, then resolves references
   between variables:

   | Layer | Applies to |
   | --- | --- |
   | `variables/common.json` | every pipeline, every environment |
   | `variables/<environment>.json` | every pipeline, one environment |
   | `overrides.common` in `pipelines/<pipeline>.variables.json` | one pipeline, every environment |
   | `overrides.<environment>` in the same file | one pipeline, one environment |

5. **Select.** It keeps every scanned name the environment defines, every overridden name and
   every extra key. Scanned names that no variable file defines, such as `Build.BuildNumber` or a
   variable declared in the YAML itself, are skipped.
6. **Write.** One file per environment: `pipelines/variables/<pipeline>/<environment>.yml`.

What the scan recognises:

| Where | Pattern | Example |
| --- | --- | --- |
| Pipeline and templates | macro syntax | `$(WebAppName)` |
| | template expression, runtime expression, condition | `${{ variables.WebAppName }}`, `variables.WebAppName` |
| | index syntax | `variables['WebAppName']` |
| | local template, followed | `- template: templates/deploy.yml` |
| Apps the pipeline deploys | token | `#{KeyVaultUri}#` |

A template path with an expression (`${{ }}`) or from another repository (`@`) is not followed.
Neither are the generated files themselves: they are output, not input.

The tokens of the apps are included so that the generated files show every value the deployment
of the app depends on. `Build-AppConfiguration.ps1` still reads `app-configuration/variables/`
directly; the generated files do not feed it.

## The generated file

```yaml
# AUTO-GENERATED by app-configuration/New-PipelineVariables.ps1. Do not edit this file.
# Pipeline 'orders-api', environment 'prod'. Change app-configuration/variables/ or
# pipelines/orders-api.variables.json, then run the generator again.
variables:
  AppConfigurationStoreName: 'appcs-orders-prod'
  EnvironmentName: 'prod'
  LogLevel: 'Warning'
  PaymentsTimeoutSeconds: '10'
  WebAppName: 'app-orders-prod'
```

- The first line marks the file as generated. **Never edit a generated file.** The next run
  overwrites it, and the drift check fails until it does. Change the source and regenerate.
- The generator only deletes a file that starts with `# AUTO-GENERATED`. A file you wrote yourself
  in the same folder is left alone.
- Every value is a single-quoted string, because every pipeline variable is a string. A `'` in a
  value is written as `''`.
- A pipeline that uses no variable gets `variables: {}`.

## Using it in a pipeline

The sample pipeline loads the file of the environment in each deploy stage:

```yaml
- ${{ each environment in parameters.environments }}:
  - stage: Deploy_${{ environment.name }}
    variables:
    - template: variables/orders-api/${{ environment.name }}.yml
    jobs:
    - template: templates/deploy-environment.yml
      parameters:
        appName: orders-api
        environment:
          name: ${{ environment.name }}
          serviceConnection: ${{ environment.serviceConnection }}
          storeName: $(AppConfigurationStoreName)
          resourceGroup: $(ResourceGroupName)
          webAppName: $(WebAppName)
```

Use the macro syntax `$(Name)` in task inputs and scripts; it is replaced when the step runs.
Values that Azure DevOps needs while it compiles the pipeline stay in the YAML: the service
connection of a task (it is authorised before the run starts), the environment of a deployment
job, stage and job names.

## The settings file

`pipelines/<pipeline>.variables.json` is optional. Its schema is
`app-configuration/schemas/pipelinevariables.schema.json`.

```json
{
  "$schema": "../app-configuration/schemas/pipelinevariables.schema.json",
  "apps": [ "orders-api" ],
  "overrides": {
    "common": { "WebAppName": "app-orders-#{EnvironmentName}#" },
    "prod": { "WebAppName": "app-orders-live" }
  },
  "extraKeys": [ "FreeShippingThreshold" ]
}
```

| Property | Meaning |
| --- | --- |
| `apps` | The apps under `app-configuration/apps/` whose tokens are included. Default: the app with the same name as the pipeline, if it exists. An app that does not exist is an error. |
| `overrides.common` | Values for this pipeline in every environment. They win over the variable files. |
| `overrides.<environment>` | Values for this pipeline in one environment. They win over `overrides.common`. An environment without a variable file is ignored, with a warning. |
| `extraKeys` | Names to include although the scan does not find them. A name an environment does not define is written with an empty value, with a warning. `*` includes every variable. |

An override may refer to other variables with `#{Name}#`; references are resolved after all layers
are merged. An overridden variable is always included, even when the scan does not find it.

## Names Azure Pipelines accepts

The variable files allow names that a pipeline cannot hold. The generator stops with an error
rather than write a file Azure DevOps reads differently:

| Problem | Example | Why |
| --- | --- | --- |
| Names that differ only in case | `LogLevel` and `loglevel` | pipeline variable names are not case-sensitive |
| Characters other than letters, digits, `.` and `_` | `Base-Url` | not a valid pipeline variable name |
| A reserved prefix | `secretToken`, `endpoint.url` | Azure Pipelines reserves `endpoint`, `input`, `secret`, `path` and `securefile` |
| A line break in a value | `"line 1\nline 2"` | a variable holds one line |

## Deterministic output

The same input gives the same bytes on every machine, so the drift check never fails on noise:

- Names are sorted ordinally, ignoring case; environments and pipelines ordinally.
- Numbers use `.` as decimal separator and booleans are `true`/`false`, whatever the culture of
  the machine (the same conversion as the tokens).
- LF line endings, a final newline, UTF-8 without BOM, no timestamps.
- A file is only written when its content changes. A second run changes nothing.
- The comparison ignores CRLF versus LF, so a checkout with `core.autocrlf` is not drift.
  `.gitattributes` keeps `pipelines/variables/**` LF in the repository.

## Running it

```powershell
# Every pipeline
./app-configuration/New-PipelineVariables.ps1

# One pipeline
./app-configuration/New-PipelineVariables.ps1 -Pipeline orders-api

# Only the pipelines that the changed files affect
./app-configuration/New-PipelineVariables.ps1 -StagedFiles (git diff --cached --name-only)

# Show what would change, write nothing
./app-configuration/New-PipelineVariables.ps1 -WhatIf

# Drift check: write nothing, exit 1 and list the files that differ
./app-configuration/New-PipelineVariables.ps1 -Check
```

`-StagedFiles` maps each changed path to the pipelines whose output it affects:

| Changed | Regenerates |
| --- | --- |
| `app-configuration/variables/`, the schema, the generator or its library | every pipeline |
| `pipelines/<pipeline>.yml` or `pipelines/<pipeline>.variables.json` | that pipeline; its output is deleted when the pipeline is deleted |
| a template under `pipelines/` | every pipeline that includes it |
| `app-configuration/apps/<app>/` | every pipeline that deploys the app |
| `pipelines/variables/<pipeline>/` | that pipeline, which undoes a hand edit |
| anything else | nothing |

## Before the commit

`.githooks/pre-commit` runs the generator with `-StagedFiles` when a staged change touches the
configuration or `pipelines/`. When that changes a generated file, the commit stops:

```text
pre-commit: the generated pipeline variables changed:
  pipelines/variables/orders-api/prod.yml
pre-commit: review them, run 'git add pipelines/variables' and commit again.
```

The hook does not stage the files itself. The generator reads the working tree, not the staged
content; with a partly staged change, adding its output silently would commit generated files that
do not match the commit. Stopping costs one extra `git add`, and you see the diff first.

## The drift check

The hook is a convenience: it can be skipped, or not be enabled at all. The gate is
`-Check` in CI, in `.github/workflows/ci.yml` and in the Validate stage of the Azure DevOps sample
(`pipelines/templates/validate.yml`). It regenerates everything in memory and fails when the
committed files differ. Because it writes nothing, it is safe on a pull request.

## Pitfalls

- **A variable that refers to another with `$(Name)`.** Write `#{Name}#` instead. The generator
  resolves tokens; `$(Name)` would be passed on as text and only expanded by Azure DevOps at run
  time, if a variable of that name happens to exist.
- **A name the scan cannot see.** A name built at run time (`variables[format(...)]`), used in a
  template from another repository or only inside a script file: add it to `extraKeys`.
- **Secrets.** The generated files are committed. Keep secrets in Key Vault, as for the apps; the
  variable may hold the vault URI.
- **A merge conflict in a generated file.** Do not resolve it by hand. Take either side, run the
  generator and commit the result.
- **Different PowerShell versions writing different bytes.** Sorting, number formatting and the
  BOM differ between PowerShell editions and cultures. This generator requires PowerShell 7.2 or
  later and fixes all three. If you port it to Windows PowerShell 5.1 as well, test that both
  write identical files, or the drift check fails depending on who ran it.
- **A variable that also exists in the YAML.** A stage-level variable from the template and a
  variable of the same name declared in the pipeline do not merge: the one in the most specific
  scope wins. Keep each name in one place.
